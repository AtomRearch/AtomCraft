# Human-centered release notes

把已确认的产品改动写成读者能理解、能使用的更新说明。说明重要选择的缘由，让语气从具体事实与适当细节中形成。

## 获取素材

从用户提供的变更、issue、diff 或产品记录中提取：实际发生的行为变化、适用版本、已验证的范围，以及需要读者采取的动作。按任务需要读取材料；素材不足但不妨碍起草时继续写，将影响准确性的待确认事项放在单独的编辑备注。

受众、渠道和篇幅优先遵循用户要求；没有指定时，沿用现有产品语气，以简短中文面向现有用户起草。它是产品更新说明任务的指导；完整的技术 changelog 或事故报告应保留各自需要的结构与细节。

## 选择与组织

- 先找出会改变读者使用体验的重要变化。重大限制、兼容性变化和读者需要做的事应清楚可见。
- 对值得解释的变化，用合适的篇幅连接使用情境、具体改动和可支持的价值；小修复可以一两句完成，无需为每项改动编故事。
- 真实用户反馈、团队决策和个人经历都需要素材支持。代码通常能说明行为，不能独自证明团队动机或用户感受。来源没有提供动机时，描述行为即可。
- 将“已实现”“已测试”“计划中”区分清楚。有关速度、稳定性或普遍用户效果的断言应有相应证据；避免用预期收益代替已验证结果。
- 作者署名或工作之外的短段落仅在素材真实、允许公开且适合渠道时使用。按内容自然收尾。

## 写作

用实际动作、物件与情境表达变化。让一个段落完成一个意思，优先说明这次更新与读者的关系。为操作步骤、并列修复或兼容性信息使用列表。保留重要版本、平台条件和限制。

产品沟通可以有温度，也可以很短。让具体内容决定长度与语气；不要把某个品牌的措辞或固定栏目当作所有产品的标准。

科研软件或工具更新涉及科学结果时，分别说明软件行为、技术验证与科学解释。演示、类比或单个案例不足以支持普遍的科研结论。

## 交付与检查

交付可直接使用的正文；有影响准确性的空缺时，在正文之外提供简短的编辑备注。除非用户要求，同时给出多个版本通常没有必要。

检查：读者能否说清有什么变化、何时可用、自己是否需要操作？行为与限制是否符合材料？有无虚构动机、经历或验证结果？语气是否适合受众？解释是否提供了有用信息？
